# Preserve an externally maintained object identifier

**Target group:** Deployments that provision users and groups into the openDesk IAM from an external
IAM and write that IAM's identifier into the `univentionObjectIdentifier` of the created objects,
e.g. to recognize their own objects again on the next synchronization run.

This guide assumes that your `kubectl` is configured with access to the Kubernetes cluster, that the
variable `$NAMESPACE` contains the namespace openDesk is deployed to and that `$ENVIRONMENT`
contains the Helmfile environment to deploy.

## Why this is needed

With openDesk 1.18.0 the `univentionObjectIdentifier` becomes openDesk's own identifier for an IAM
object, and it is the identifier the OX Connector addresses its accounts by from this release on,
see [OX App Suite: The provisioning moves to the IAM object identifier](../migrations-manual.md#ox-app-suite-the-provisioning-moves-to-the-iam-object-identifier).

The automated action [`ldap_entryuuid_to_object_identifier`](../migrations-automated.md#ldap_entryuuid_to_object_identifier)
of `migrations-pre` therefore overwrites the `univentionObjectIdentifier` of **every** object that
carries one with that object's own `entryUUID`. Whatever your synchronization wrote there is
overwritten with the upgrade, and the log of the `migrations-pre` Job is the only record of the
previous values.

The action cannot be skipped in a meaningful way: The components deployed right after it, the OX
Connector above all, work with the identifier it writes. An identifier of an external IAM has to
move out of the attribute instead - which is what this guide is about.

> [!note]
> This only affect existing deployments. New deployments after v1.18.0 can make use of the
> univentionObjectIdentifier as long as they respect the UUID format that is technically enforced.

## The reserved attribute

For this case openDesk reserves the LDAP attribute `univentionFreeAttribute2` and ships it, from
1.18.0 on, as the UDM extended attribute `reservedLegacyExternalIamIdentifier`:

| Property       | Value                                                        |
| -------------- | ------------------------------------------------------------ |
| UDM property   | `reservedLegacyExternalIamIdentifier`                        |
| LDAP attribute | `univentionFreeAttribute2`                                   |
| Object class   | `univentionFreeAttributes`                                   |
| UDM modules    | `users/user`, `groups/group`                                 |
| Syntax         | `UUID`                                                       |
| May change     | No - the value can be set once and not be changed afterwards |

openDesk itself neither reads nor writes this attribute; it exists so that your identifier has a
place to live that openDesk will not take over in a later release. It is also indexed to avoid performance issues.

> [!important]
> The extended attribute is created by the upgrade, but your identifiers have to be saved *before*
> `migrations-pre` overwrites them. You therefore create the attribute yourself first, with the
> definition below which mirrors the one openDesk ships, so that the upgrade finds it as it expects
> it and changes nothing about it.

## Overview

The whole procedure, with the upgrade in the middle of it:

1. [Stop the synchronization](#step-1-stop-the-synchronization) from your external IAM.
2. [Create the extended attribute](#step-2-create-the-extended-attribute)
   `reservedLegacyExternalIamIdentifier` through the UDM REST API.
3. [Copy the identifiers](#step-3-copy-the-identifiers) of all users and groups from
   `univentionObjectIdentifier` into the new attribute.
4. [Reconfigure the synchronization](#step-4-reconfigure-the-synchronization) to write and match on
   `reservedLegacyExternalIamIdentifier` instead of `univentionObjectIdentifier`.
5. [Upgrade openDesk](#step-5-upgrade-opendesk) to 1.18.x.
6. [Restart the synchronization](#step-6-restart-the-synchronization), after a grace period of about
   30 minutes.

The synchronization stays stopped from step 1 to step 6. Nothing else in openDesk is paused by this
procedure; steps 1 to 4 can be done well ahead of the upgrade.

## Preparation

The identifiers are moved through the [UDM REST API](../architecture/apis.md#udm-rest-api), the
interface every other change to the IAM goes through as well. It is an in-cluster service, so unless
you have made it available externally (`functional.externalServices.nubus.udmRestApi.enabled`), you
reach it through a port forwarding:

```bash
kubectl -n "$NAMESPACE" port-forward service/ums-udm-rest-api 9979:9979
```

In a second shell, set up what the calls below need. The LDAP admin `cn=admin` is used here because
it is the account the IAM's own components work with; an account of the group `IAM API - Full
Access` works just as well:

```bash
# The LDAP base DN for openDesk
export LDAP_BASE_DN="dc=swp-ldap,dc=internal"
# The UDM REST API through the port forwarding above.
export UDM_URL="http://localhost:9979/univention/udm/"
export UDM_USERNAME="cn=admin"
export UDM_PASSWORD="$(kubectl -n "$NAMESPACE" get secret ums-ldap-server-admin \
  -o jsonpath='{.data.password}' | base64 -d)"
```

Check that the API answers and that the container the extended attribute goes into exists - it does
in every openDesk deployment from 1.17.0 on:

```bash
curl -fsS -u "${UDM_USERNAME}:${UDM_PASSWORD}" -H "Accept: application/json" \
  "${UDM_URL}container/cn/?filter=(cn=opendesk)&scope=sub" \
  | jq -r '._embedded."udm:object"[].dn'
```

It answers with the container the openDesk extended attributes live in:

```text
cn=opendesk,cn=custom attributes,cn=univention,dc=swp-ldap,dc=internal
```

> [!note]
> Should the container `cn=opendesk,cn=custom attributes,cn=univention,$LDAP_BASE_DN` not exist,
> your deployment is older than 1.15.0. Complete the
> [mandatory upgrade path](../migrations-manual.md#overview-and-mandatory-upgrade-path) first.

## Step 1: Stop the synchronization

Stop whatever writes objects from your external IAM into the openDesk IAM e.g. the
[Nubus Directory Importer](https://docs.software-univention.de/nubus-kubernetes-operation/1.x/en/connect-external-iam/directory-importer.html),
your own integration against the UDM REST API, or whichever tooling you use.

It must stay stopped until [step 6](#step-6-restart-the-synchronization). Two things depend on it:
The copy in step 3 works on a directory that does not change underneath it, and a synchronization
still writing `univentionObjectIdentifier` after the upgrade would collide with the identifier
openDesk maintains there now.

## Step 2: Create the extended attribute

Create `reservedLegacyExternalIamIdentifier` with exactly this definition. It is the definition
openDesk ships from 1.18.0 on, so the upgrade finds the attribute as it expects it:

```bash
curl -fsS -u "${UDM_USERNAME}:${UDM_PASSWORD}" \
  -X POST "${UDM_URL}settings/extended_attribute/" \
  -H "Accept: application/json" \
  -H "Content-Type: application/json" \
  --data @- <<EOF
{
  "position": "cn=opendesk,cn=custom attributes,cn=univention,${LDAP_BASE_DN}",
  "properties": {
    "name": "reservedLegacyExternalIamIdentifier",
    "CLIName": "reservedLegacyExternalIamIdentifier",
    "ldapMapping": "univentionFreeAttribute2",
    "groupName": "External IAM",
    "module": ["users/user", "groups/group"],
    "shortDescription": "Identifier from external IAM",
    "longDescription": "Reserved for customers that have been using univentionObjectIdentifier before the consolidation in openDesk that came with v1.18.0 and require an alternative attribute to move their univentionObjectIdentifier data to. This attribute is not used by openDesk itself.",
    "tabName": "External IAM",
    "syntax": "UUID",
    "mayChange": false,
    "deleteObjectClass": true,
    "objectClass": "univentionFreeAttributes",
    "doNotSearch": false,
    "disableUDMWeb": true
  }
}
EOF
```

Verify that the attribute exists and reaches the modules it has to reach:

```bash
curl -fsS -u "${UDM_USERNAME}:${UDM_PASSWORD}" -H "Accept: application/json" \
  "${UDM_URL}settings/extended_attribute/?filter=(name=reservedLegacyExternalIamIdentifier)" \
  | jq '._embedded."udm:object"[].properties | {name, ldapMapping, module, syntax}'
```

The property becomes available on user and group objects within seconds. A user object read through
the API carries it from then on:

```bash
curl -fsS -u "${UDM_USERNAME}:${UDM_PASSWORD}" -H "Accept: application/json" \
  "${UDM_URL}users/user/?filter=(uid=Administrator)&properties=*" \
  | jq '._embedded."udm:object"[0].properties.reservedLegacyExternalIamIdentifier'
```

It answers with `null`: the property is there and is empty, which is what step 3 fills.

> [!note]
> The value of the attribute is validated against the UDM syntax `UUID` the same was as the
> `univentionObjectIdentifier` is.

## Step 3: Copy the identifiers

The copy walks the user and group objects that carry a `univentionObjectIdentifier` and writes that
value into `reservedLegacyExternalIamIdentifier`. The helper script
[`1.18.0-external-iam-identifier.py`](../migrations-helper/1.18.0-external-iam-identifier.py) does
this through the UDM REST API. It needs nothing but Python 3, it takes `UDM_URL`, `UDM_USERNAME` and
`UDM_PASSWORD` from the environment prepared above, it reports before it writes, and it can be run
again: objects whose identifiers already match are left alone.

Look at what it would do first:

```bash
python3 docs/migrations-helper/1.18.0-external-iam-identifier.py --dry-run
```

The report ends with one line per module, e.g.:

```text
users/user: 1289 object(s) to copy, 0 already copied, 3 without an identifier, 0 conflict(s).
groups/group: 214 object(s) to copy, 0 already copied, 0 without an identifier, 0 conflict(s).
```

Because the attribute is defined as not changeable, a value that is written wrongly cannot simply be
corrected afterwards. Write a single object first and check it:

```bash
python3 docs/migrations-helper/1.18.0-external-iam-identifier.py --limit 1
```

> [!note]
> Should UDM reject even this first write - with a message about a value that may not change, or
> about the syntax of the value - do not work around it by changing the definition of the extended
> attribute: the upgrade applies openDesk's definition over yours. Clarify it with openDesk support
> before you upgrade.

Then copy everything:

```bash
python3 docs/migrations-helper/1.18.0-external-iam-identifier.py
```

The script fails with a non-zero exit code when an object cannot be written or when it ends with
conflicts. It re-reads every object it wrote and verifies the value; do not continue with a run
that did not report success.

Should you rather do the copy yourself: For one object it is a `GET` of the object, the value of
`univentionObjectIdentifier` set as `reservedLegacyExternalIamIdentifier`, and a `PUT` of the full
representation back, guarded by the `ETag` the `GET` returned.

## Step 4: Reconfigure the synchronization

Point your synchronization at the new attribute, so that it no longer touches
`univentionObjectIdentifier`:

- Everything that **writes** the external identifier writes
  `reservedLegacyExternalIamIdentifier` (LDAP: `univentionFreeAttribute2`).
- Everything that **searches** for an object by the external identifier searches for
  `reservedLegacyExternalIamIdentifier`.

For the Nubus Directory Importer this is the attribute mapping of its configuration; for an own
integration it is wherever the identifier is mapped.

## Step 5: Upgrade openDesk

Upgrade to openDesk 1.18.0 as described in [`migrations-manual.md`](../migrations-manual.md),
including all other manual steps of this release.

`migrations-pre` writes the `entryUUID` of every object into its `univentionObjectIdentifier` while
this runs, and reports each change in its log. Your identifiers are, at this point, in
`reservedLegacyExternalIamIdentifier` and untouched by it.

## Step 6: Restart the synchronization

Wait about **30 minutes** after the upgrade has finished before you start the synchronization again.

openDesk 1.18.0 adds `univentionFreeAttribute2` to the equality indices of the LDAP server. Until
that index has been created, every search filtering on the attribute is a full scan of the directory
- which, on a directory of the size that makes this migration relevant, is slow enough to let a
synchronization run into its own timeouts, and puts avoidable load on the LDAP server while the
deployment is still settling.

If your synchronization cannot be paused for that long, have the index in place before the upgrade
instead, by overriding `global.ldap.index.eq` of the Nubus release with the value openDesk 1.18.0
ships (see [`values-nubus.yaml.gotmpl`](../../helmfile/apps/nubus/values-nubus.yaml.gotmpl)) - the
list has to be given completely, an index cannot be added to it on its own.

Afterwards, verify on a handful of objects that the synchronization matches its own objects again
rather than creating them a second time.
